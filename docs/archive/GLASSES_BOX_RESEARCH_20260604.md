# 眼镜盒子项目 — 前期调研与技术选型报告

> 归档日期：2026-06-04
> 调研范围：WEO PC 工具（参考源） · 安卓手表ADB工具箱（参考源）
> 产出目标：GlassesBox — 独立商业级智能眼镜管理平台
> 原则声明：本工程为完全独立项目，不会对 WEO 奥贝之眼工程做任何修改。

---

## 一、调研背景

本次调研对两个参考源进行了完整的技术审计，目标是提取可借鉴的通用能力、识别需要规避的设计耦合，以及为新工程 GlassesBox 的技术选型提供决策依据。

**参考源 A：WEO PC 工具（`F:\TOOLS\Wisdom Eye of Obwiler\pc_tool\`）**

- 框架：PySide6 (Qt for Python 6)
- 核心能力：ADB 设备管理、scrcpy 屏幕镜像（Win32 HWND 嵌入）、文件管理、Shell 终端、截图
- 规模：约 2500 行 Python，9 个核心模块 + 7 个 UI 面板
- 耦合问题：硬编码了 `com.obwiler.weo` 包名、AI 配置流水线、WEO 部署流程

**参考源 B：安卓手表 ADB 工具箱（`D:\APP\WaiShe\TongYong\AndroidWatch_ADB_ToolBox\`）**

- 形态：已编译 tkinter 单文件 exe（Python 3.6）
- 功能推断：ADB 调试、应用商店（APK 批量缓存）、媒体控制面板
- 局限：闭源制品，无法直接阅读源码；商店模式不适合眼镜设备

## 二、可继承的技术资产

从 WEO 工具中识别出以下**框架级通用能力**，将采用"重写+增强"而非"直接拷贝"的方式纳入 GlassesBox：

| 能力模块 | 原实现 | GlassesBox 策略 |
|----------|--------|----------------|
| ADB 客户端 | `adb_client.py` — 子进程封装，retry 机制 | 保留核心思路，用更现代的 async/await 或 QThread 模式重写 |
| 设备管理 | `device.py` — QTimer 轮询 + DataClass 快照 | 重写，增加更丰富的系统指标采集 |
| 屏幕镜像 | `scrcpy.py` — Win32 SetParent HWND 嵌入 | 保留方案，优化嵌入性能和重连机制 |
| 文件管理 | `file_mgr.py` — `ls -la` 解析 | 保留方案，增强目录树展示 |
| Shell 终端 | `shell.py` — 历史 + 危险命令拦截 | 保留方案，增加语法高亮 |
| 截图 | `screenshot.py` — `exec-out screencap` | 保留方案 |
| 主题引擎 | `theme.py` — JSON 驱动 QSS 生成 | 完全重写，走向精品质感 |

**关键决策：不直接拷贝代码，而是在理解其设计意图的基础上重新实现。** 这样可以彻底消除 WEO 的命名空间污染，同时利用这次机会提升代码质量和架构清晰度。

## 三、参考源的局限与回避

**WEO 工具中需要回避的设计：**
- `constants.py` 的硬编码包名模式 — GlassesBox 采用零硬编码、全自动检测
- AI 配置面板的臃肿表单 — 不属于通用眼镜管理范畴
- 一键部署流水线 — 眼镜盒子不做 APK 分发

**手表工具箱中需要回避的设计：**
- APK 应用商店模式 — 涉及分发合规风险，分散核心定位
- tkinter 原生控件 — 视觉表现力不足以支撑商业级产品的审美要求
- 编译闭源交付 — GlassesBox 优先保持源码透明

---

## 四、GlassesBox 产品定位

**一句话：** 面向智能眼镜开发者和高级用户的商业级设备管理平台。

**差异化竞争点：**

1. **实时监控"后门"** — 不是简单的设备信息展示，而是眼镜运行状态的持续实时感知：后台进程、前台焦点、CPU/内存曲线、logcat 实时流
2. **精品质感** — 超越工具类软件的视觉标准，对标 macOS 系统工具或专业 IDE 的 Dark UI
3. **即插即用** — 不依赖眼镜端预装任何特定 APK，纯 ADB 通道运作
4. **操作愉悦** — 保留 WEO 验证过的 D-Pad + scrcpy 交互模型，增加 iPod Click Wheel 等有质感的控制方式

## 五、技术选型

| 维度 | 选择 | 理由 |
|------|------|------|
| GUI 框架 | PySide6 | Qt 的渲染质量和组件丰富度远超 tkinter；HWND 嵌入已有成熟方案 |
| 屏幕镜像 | scrcpy v2.x 嵌入 | 40-70ms 延迟可接受；SDL 窗口可通过 Win32 API 无缝嵌入 |
| 异步模型 | QThread + Signal/Slot | 避免阻塞 UI；Qt 原生方案，无需额外依赖 |
| 数据持久化 | JSON + %APPDATA% | 轻量，不引入数据库依赖 |
| 打包 | PyInstaller | 已验证可用 |
| 设计语言 | 自研 Dark Pro 主题 | 深色基调 + 低饱和 accent + 精细间距系统；借鉴但不复制任何现有设计系统 |

## 六、建议开发策略

采用 **垂直切片** 方式：每个 Phase 产出一个完整可运行的独立功能，而非先搭架子后填内容。

1. **Phase 1 — 框架底座：** 启动窗口、主题引擎、设备连接 → 可运行的最小骨架
2. **Phase 2 — 监控后门：** 进程/焦点/资源/日志四维面板 → 核心差异化价值交付
3. **Phase 3 — 控制与镜像：** iPod Click Wheel + scrcpy 嵌入 → 交互闭环
4. **Phase 4 — 工具链补全：** 文件管理、Shell、截图 → 完整工具箱
5. **Phase 5 — 精致打磨：** 动画、过渡、快捷键、图标、打包
